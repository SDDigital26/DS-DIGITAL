# 2. Пошаговый план работы ИИ по ТЗ

## Шаг 0. Зафиксировать правила проекта

ИИ загружает и принимает как обязательные документы:

- полное ТЗ;
- строгую инструкцию для ИИ-разработчика;
- прототип первого экрана;
- список согласованных решений;
- список полученных материалов от владельца.

ИИ не начинает кодирование, пока не понимает, какой релиз выполняется: R1, R2 или R3.

ИИ создаёт файл `DECISIONS.md`, где фиксирует утверждённые решения, открытые вопросы и запрещённые предположения.

## Шаг 1. Осмотреть существующее окружение

Перед изменениями ИИ проверяет:

- структуру репозитория;
- текущую ветку Git;
- незакоммиченные изменения;
- package.json;
- переменные окружения;
- конфигурацию Next.js;
- существующие страницы и компоненты;
- базу данных и миграции;
- Docker-конфигурацию;
- текущие тесты и команды запуска.

Если проект уже существует, ИИ не создаёт новый проект поверх него и не удаляет текущую реализацию.

## Шаг 2. Создать безопасную точку возврата

До начала каждой крупной задачи ИИ:

1. Проверяет состояние Git.
2. Создаёт отдельную ветку.
3. Делает контрольный commit только уже согласованных изменений.
4. Проверяет, что `.env`, токены, пароли и персональные данные не попадут в Git.
5. Делает backup базы данных перед изменением схемы.

Production, домен, DNS и рабочую базу нельзя изменять без отдельного подтверждения владельца.

## Шаг 3. Разбить работу на маленькие задачи

Одна задача должна затрагивать одну логическую область. Например:

- header;
- hero;
- карточки услуг;
- локализация;
- форма;
- база заявок;
- CMS;
- SEO;
- тестирование.

Перед каждой задачей ИИ пишет коротко: что меняет, какие файлы затрагивает, что не меняет и как проверит результат.

## Шаг 4. Собрать базовый R1 без тяжёлых эффектов

Сначала реализуются быстрые и стабильные версии:

- layout;
- header;
- hero с текстом и CTA;
- услуги;
- проекты;
- контакты;
- footer;
- адаптивная сетка;
- RU/EN;
- базовые страницы услуг.

На этом этапе 3D, частицы и молния не должны блокировать работу сайта. Hero должен работать со статичным постером или без декоративной графики.

## Шаг 5. Реализовать дизайн-систему

ИИ создаёт единые токены цветов, шрифтов, отступов, радиусов, теней и состояний компонентов.

Используются только согласованные цвета DS DIGITAL. Новый логотип, новые фирменные цвета и новый визуальный стиль без разрешения не создаются.

Все кнопки и интерактивные элементы получают состояния hover, focus, active, disabled и loading.

## Шаг 6. Добавить локализацию

ИИ подключает RU и EN с URL `/ru/` и `/en/`.

Переводятся:

- навигация;
- hero;
- услуги;
- формы;
- ошибки;
- сообщения об успехе;
- FAQ;
- юридические страницы;
- SEO-метаданные.

Смешанный язык на одной опубликованной странице запрещён.

## Шаг 7. Добавить форму и сохранение заявок

Форма сначала получает клиентскую валидацию, затем серверную валидацию по той же схеме.

Порядок обработки:

1. Пользователь заполняет форму.
2. Проверяется согласие на обработку данных.
3. Проверяется антиспам.
4. Сервер валидирует поля.
5. Заявка сохраняется в PostgreSQL.
6. Заявка попадает в очередь уведомлений.
7. Telegram-уведомление отправляется отдельно.
8. Пользователь получает подтверждение.

Если Telegram недоступен, заявка всё равно сохраняется. Ошибка уведомления не должна удалять или отменять заявку.

## Шаг 8. Подключить CMS только после стабильной витрины

CMS подключается после того, как основная публичная часть работает.

В CMS должны редактироваться только согласованные сущности:

- услуги;
- проекты;
- страницы;
- медиа;
- SEO-поля;
- контакты;
- заявки;
- настройки каналов.

ИИ не добавляет самописную админку, если утверждена Payload CMS или другое готовое решение.

## Шаг 9. Добавить эффекты после измерения скорости

После базового Lighthouse-теста ИИ подключает:

- 3D hero;
- canvas-молнию;
- частицы;
- плавные переходы;
- микроанимации.

Каждый эффект подключается отдельно. После каждого эффекта повторно проверяются LCP, INP, CLS, FPS, мобильные устройства и `prefers-reduced-motion`.

Если эффект ухудшает показатели, он упрощается или отключается в lite-режиме.

## Шаг 10. Проверить R1

Проверяются:

- главная;
- все страницы услуг;
- RU/EN;
- форма;
- сохранение заявки;
- Telegram-очередь;
- мобильное меню;
- якорные ссылки;
- юридические документы;
- cookie-согласие;
- SEO;
- клавиатурная навигация;
- Chrome, Firefox, Safari и Edge;
- iPhone Safari и Android Chrome.

## Шаг 11. Только после приёмки переходить к R2

R2 начинается только после подтверждения владельца, что R1 принят.

До R2 нельзя самостоятельно добавлять калькулятор, CRM, цены, отзывы, рекламу и сложные воронки.

## Шаг 12. Только после отдельного согласования переходить к R3

R3 начинается только после утверждения AI-провайдера, бюджета, лимитов, источников знаний и правил безопасности.

AI-консультант не подключается наугад и не получает доступ к рабочей базе или секретам.

# 3. Контроль после каждой задачи

ИИ обязан предоставить отчёт:

**Сделано:** какие изменения внесены.  
**Файлы:** какие файлы изменены.  
**Проверки:** какие команды и сценарии запущены.  
**Не изменялось:** что намеренно осталось нетронутым.  
**Риски:** какие проблемы остаются.  
**Нужно согласовать:** конкретные вопросы к владельцу.

Фраза «готово» разрешена только после проверки сборки и основных пользовательских сценариев.

# 5. Главное правило для ИИ

ИИ работает только по текущему релизу, меняет минимально необходимое, не придумывает данные, не удаляет рабочее, не подключает платные сервисы без согласования и не переходит к следующему этапу без приёмки предыдущего.

# 6. Экономный режим работы ИИ

Этот режим обязателен для всех задач DS DIGITAL. ИИ не должен заново читать весь проект перед каждой маленькой правкой и не должен повторять уже выполненный анализ.

## 6.1. Правило короткого контекста

Перед задачей ИИ читает только относящиеся к ней файлы. Для изменения header не нужно повторно анализировать базу данных, CMS и весь backend. Для изменения формы не нужно заново изучать все визуальные компоненты.

ИИ использует краткое состояние проекта в файле `PROJECT_STATE.md`. После каждой завершённой задачи он обновляет только изменившиеся пункты: текущий релиз, выполненные задачи, открытые вопросы и известные ошибки.

## 6.2. Формат начала задачи

Перед выполнением ИИ пишет не больше пяти строк:

1. Цель задачи.
2. Файлы, которые будут проверены.
3. Файлы, которые могут быть изменены.
4. Что намеренно не затрагивается.
5. Как будет выполнена проверка.

Если задача понятна и не требует решения владельца, ИИ сразу выполняет её. Вопрос задаётся только при реальном блокере, неоднозначном решении или риске потери данных.

## 6.3. Формат завершения задачи

Отчёт должен быть коротким:

```text
Готово: [результат]
Изменено: [файлы]
Проверено: [команда или сценарий]
Риски: [нет / список]
Дальше: [следующая маленькая задача]
```

Запрещены длинные пересказы всего ТЗ после каждой правки.

## 6.4. Экономия на инструментах

ИИ сначала использует уже подключённые навыки и существующие компоненты. Не создаёт новый компонент, если подходящий уже есть. Не ищет библиотеку, если задача решается текущим стеком. GitHub Gem Seeker применяется только для универсальной задачи, которую неразумно писать самостоятельно.

Web Design Reviewer запускается после законченного визуального блока, а не после каждого изменения цвета или отступа. Lighthouse запускается после группы изменений, а не после каждой строки.

## 6.5. Безопасная последовательность

Сначала ИИ делает минимальную правку, затем запускает короткую проверку, затем показывает отчёт. Только после подтверждения стабильности переходит к следующему блоку. Если проверка не пройдена, ИИ исправляет только причину ошибки и не добавляет новые функции одновременно.

# 7. Структура внутренних страниц DS DIGITAL

Все внутренние страницы должны использовать общий header, footer, языковой переключатель, CTA и дизайн-систему. Внутренняя страница не должна выглядеть как отдельный несвязанный сайт.

## 7.1. Общий шаблон внутренней страницы

Каждая страница содержит:

1. SEO-метаданные и Open Graph.
2. Breadcrumbs или другое понятное указание положения в структуре сайта.
3. Hero внутренней страницы: заголовок, короткое объяснение, основной CTA.
4. Основной контентный блок.
5. Доказательства: кейсы, метрики, скриншоты или процесс — только если данные подтверждены.
6. FAQ или блок снятия возражений.
7. CTA-блок с переходом к форме.
8. Footer и юридические ссылки.

## 7.2. Страница услуги

URL: `/ru/services/[slug]` и `/en/services/[slug]`.

Структура:

- название услуги и результат для клиента;
- кому услуга подходит;
- какую проблему решает;
- состав работ;
- этапы процесса;
- используемые технологии;
- возможные сроки только после подтверждения;
- связанные кейсы;
- FAQ;
- форма с автоматически выбранной услугой.

Нельзя публиковать выдуманные цифры, клиентов, сроки, логотипы и результаты. Если данных нет, блок должен быть скрыт или помечен как демонстрационный.

## 7.3. Страница проекта и кейса

URL: `/ru/projects/[slug]` и `/en/projects/[slug]`.

Структура:

- название проекта;
- тип проекта;
- задача клиента;
- исходная ситуация;
- решение DS DIGITAL;
- этапы реализации;
- визуальные материалы;
- технологии;
- результат;
- ограничения и оговорки;
- CTA на похожую услугу;
- ссылки на следующий и предыдущий кейс.

Для каждого кейса в CMS нужны поля: название RU/EN, slug, обложка, галерея, краткое описание, полное описание, услуги, технологии, дата, статус публикации, SEO Title, SEO Description и разрешение на публикацию.

## 7.4. Страница «О компании»

Структура:

- позиционирование DS DIGITAL;
- принципы работы;
- компетенции;
- процесс взаимодействия;
- команда — только при наличии подтверждённых материалов;
- технологии;
- CTA.

Страница не должна превращаться в длинную биографию. Её задача — повысить доверие и объяснить подход.

## 7.5. Страница контактов

Структура:

- короткий CTA;
- Telegram и другие согласованные каналы;
- email, если опубликован;
- форма заявки;
- часы ответа, только если они утверждены;
- юридическая информация;
- карта только при необходимости.

Контактные данные не дублируются в разных местах с разными значениями. Источник контактных данных должен быть единым — настройки CMS или конфигурация проекта.

## 7.6. Страница FAQ

FAQ должен быть разделён по темам: услуги, процесс, сроки, стоимость, материалы от клиента, поддержка и безопасность. Вопросы и ответы хранятся в CMS или локальном контентном файле, но не дублируются в нескольких источниках.

## 7.7. Юридические страницы

Минимальный набор:

- Privacy Policy;
- Cookie Policy;
- Terms of Use;
- согласие на обработку персональных данных.

Юридический текст предоставляется или утверждается владельцем. ИИ не выдаёт автоматически сгенерированный текст за юридическую консультацию.

## 7.8. Системные страницы

Нужны отдельные состояния:

- 404 — страница не найдена;
- 500 — временная ошибка;
- offline или ошибка сети;
- success — заявка принята;
- error — заявка не отправлена;
- loading — загрузка данных;
- empty — нет проектов или результатов.

Каждое состояние должно иметь понятное действие для пользователя: вернуться на главную, повторить попытку или написать в Telegram.

# 8. Анимация и интерактивность

Анимация используется для объяснения интерфейса и усиления бренда, но не должна мешать чтению, отправке формы, SEO или скорости сайта.

## 8.1. Приоритет анимаций

Сначала реализуются дешёвые CSS-анимации. Затем — переходы между блоками. Canvas, WebGL и 3D добавляются только после проверки производительности.

Приоритет такой:

1. Hover и focus состояний.
2. Появление блоков при прокрутке.
3. Анимация мобильного меню.
4. Переходы между страницами.
5. Лёгкая интерактивность hero.
6. Частицы, молния и 3D — только как необязательный слой.

## 8.2. Hero-анимация

Основной текст и CTA должны появляться без ожидания загрузки 3D. Сначала отображается статичный fallback или лёгкий CSS-фон. 3D-объект загружается лениво после первого отображения основного контента.

Для hero обязательны:

- статичный постер;
- lite-режим для слабых устройств;
- отключение движения при `prefers-reduced-motion`;
- отсутствие блокирующего preloader;
- отсутствие критического текста внутри canvas;
- управление нагрузкой по размеру экрана и мощности устройства.

## 8.3. Анимация блоков

Карточки услуг, проектов и CTA могут использовать плавное появление, лёгкое изменение цвета границы или небольшое смещение. Запрещены резкие вспышки, постоянное движение текста, бесконечные пульсации и эффекты, мешающие нажатию.

Одинаковый эффект не должен запускаться одновременно на десятках элементов. Для длинных списков используется задержка только для первых элементов или отключается stagger-анимация.

## 8.4. Молния и частицы

Молния и частицы являются декоративными. Они не должны быть единственным способом показать действие или смысл блока. Canvas обязан иметь fallback, не должен перекрывать CTA и должен корректно удаляться при уходе со страницы.

Проверить нужно: FPS на мобильном, использование CPU/GPU, память, остановку анимации во вкладке, изменение размера окна, контраст текста и отключение эффекта в lite-режиме.

## 8.5. Доступность анимаций

При `prefers-reduced-motion: reduce` отключаются параллакс, вращение, частицы, резкие масштабирования и длинные переходы. Оставляются только быстрые изменения состояния, необходимые для понимания интерфейса.

Анимация не должна быть единственным индикатором ошибки, успеха, загрузки или фокуса. Для каждого состояния нужен текст, цветовой контраст и доступное имя.

## 8.6. Технические критерии анимации

Каждая анимация описывается таблицей:

| Элемент | Событие | Эффект | Длительность | Fallback | Отключение |
|---|---|---|---|---|---|
| Hero | загрузка | плавное появление | до 600 мс | статичный фон | reduced motion |
| Карточка | hover/focus | изменение границы | до 200 мс | без эффекта | touch |
| Mobile menu | открытие | выезд панели | до 250 мс | мгновенное открытие | reduced motion |
| CTA | hover | цвет/тень | до 200 мс | обычная кнопка | touch |
| Частицы | idle | декоративное движение | непрерывно | статичный фон | lite/reduced motion |

Допустимые значения и конкретные эффекты утверждаются в дизайн-системе. ИИ не добавляет новую анимацию только потому, что она визуально выглядит эффектно.

## 8.7. Приёмка анимаций

Анимация принимается только если:

- основной контент доступен без неё;
- сайт не ждёт загрузки эффекта;
- mobile не теряет производительность;
- нет горизонтального скролла;
- работает клавиатурный focus;
- работает reduced motion;
- нет мерцания и скачков layout;
- Lighthouse и Core Web Vitals не ухудшились сверх согласованных порогов.
